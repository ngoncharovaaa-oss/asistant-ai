# AsiStantAI — ИИ-помощник руководителя

Второй «я» руководителя подразделения онлайн-продаж: разбирает входящую почту, готовит ответы от первого лица в его стиле, собирает протоколы встреч и утренний план, а всё чувствительное оставляет человеку. Ничего не отправляется без подтверждения.

Кейс «ИИ-помощник руководителя», трек «Цифровой аватар», хакатон «ИИкузница» 2026.

Работает офлайн на синтетическом датасете организаторов: детерминированные правила разбора, без внешних API и без ключей. Тот же датасет — источник всех цифр в презентации, поэтому код и защита считают одно и то же.

## Быстрый старт

Нужен Python 3.12 и пакеты из `requirements.txt`.

На Windows проще двойным кликом: `Запустить AsiStantAI.bat` — проверит Python, при необходимости поставит зависимости, поднимет сервер и откроет дашборд в браузере.

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows; на Linux/macOS — source .venv/bin/activate
pip install -r requirements.txt

python -m app.cli run           # разобрать неделю, собрать черновики и отчёты
python -m app.cli serve         # дашборд на http://127.0.0.1:8000
pytest                          # 118 проверок движка, API и живых каналов
```

Живые каналы включаются файлом `.env` (см. `.env.example`), код при этом не меняется:

```bash
python -m app.cli channels --check   # проверить IMAP/SMTP, бота, мой Telegram, Zoom, Телемост и Битрикс24
python -m app.cli mailboxes          # ящики и непрочитанные (по умолчанию за всё время)
python -m app.cli mailboxes --period today   # период: today, 3d, 7d, 30d, all
python -m app.cli run --live         # забрать новые письма из ящиков
python -m app.cli tg-listen          # принимать команды и кнопки бота
python -m app.cli tg-login           # один раз: вход в мой Telegram по коду
python -m app.cli tg-unread          # непрочитанные в моём Telegram (по умолчанию за всё время)
python -m app.cli tg-unread --period today   # за сегодня; также 3d, 7d, 30d
python -m app.cli tg-drafts --period 7d   # черновики ответов на непрочитанные за период
python -m app.cli zoom-link --topic "Планёрка" --start "2026-11-28 10:00"  # ссылка Zoom
python -m app.cli telemost-link --topic "Планёрка" --start "2026-11-28 10:00"  # ссылка Телемоста
python -m app.cli zoom-login-url     # ссылка для входа в Zoom через приложение
python -m app.cli zoom-logout        # выйти из Zoom и удалить токены
python -m app.cli set-link --provider telemost --url https://telemost.yandex.ru/j/…  # постоянная комната
```

`run` пишет результаты в `out/`, а состояние — в `data/asistant.db`. Дашборд читает журнал и при первом открытии сам досчитывает неделю, если журнал пуст.

## Что на входе

Папка `data/kuznitsa/` — датасет организаторов: почта за 7–11 декабря 2026, календарь на две недели 7–18 декабря:

| Файл | Содержание |
|---|---|
| `inbox.csv` | 80 писем (16 в день) с колонкой `expected_action` — эталонным действием |
| `calendar.ics` | 50 встреч за две недели, включая защищённые (руководство, клиент, деньги, 1:1) |
| `tasks.csv` | 12 задач трекера, часть с просроченным сроком |
| `meetings/` | 5 саммари встреч и 5 транскриптов из архива заказчика |
| `protocols/` | 5 полных протоколов: шапка, повестка, решения, поручения, риски, шаги |
| `org_structure.csv` | 12 человек: руководитель, 7 подчинённых, его руководитель и 3 коллеги |
| `leader_profile.md` | стиль, правила делегирования и эскалации руководителя |
| `README.md` | описание набора от организаторов |

Колонка `expected_action` используется только для замера точности — классификатор её не читает.

## Как принимается решение

Порядок правил в `app/classify.py` — от жёсткого к мягкому:

1. **Чувствительная тема → «спросить руководителя».** Деньги и бюджеты, кадры, обязательства клиентам, письма руководству, стратегия, 1:1. Это ограничение не отключается настройкой: после классификации `app/pipeline.py` ещё раз проверяет риски и принудительно ставит эскалацию.
2. **Есть адресат в оргструктуре и тема в его зоне → «делегировать»** с конкретным человеком и причиной.
3. **Типовой запрос с готовым ответом в базе знаний → «авто»** (черновик готов, но отправка всё равно за человеком).
4. **Информационное письмо без действия → «игнорировать»**, статус для команды → «в сводку».

Каждое решение получает уверенность; ниже `CONFIDENCE_THRESHOLD` черновик не готовится.

## Черновики и обучение

`app/compose.py` собирает текст от первого лица по профилю руководителя: обращение, суть, срок, подпись. У каждого черновика — ссылки на источники: письмо, база знаний, встреча, задача, оргструктура.

Правка в дашборде (`POST /api/drafts/{id}/edit`) сохраняется в журнал и становится образцом для этой темы: следующие черновики той же темы собираются по исправленному тексту. Обучение — без дообучения модели и без кода.

Утверждение (`approve`) — единственная точка «отправки». На демо-датасете это мок: черновик помечается утверждённым, событие пишется в журнал, наружу ничего не уходит. На живом прогоне (`run --live`) утверждённый черновик реально уходит через SMTP того ящика, откуда пришло письмо. Отклонённый черновик утвердить нельзя.

## Протоколы встреч

`app/meetings.py` разбирает два слоя. Основной — полные протоколы из `data/kuznitsa/protocols/`: шапка (тема, дата, ведущий, участники), повестка, решения, таблица поручений с ответственными, сроками и статусом, открытые вопросы и риски, дальнейшие шаги. Если полного протокола для встречи нет, работает резервный разбор саммари: чек-листы задач, решения, открытые вопросы, ответственные (в том числе «Яне и Саше», «Speaker 2», «Маша и Ваня») и сроки («до 15.12.2026», «к следующему спринту»). Результат по архиву — 50 поручений и 41 открытый вопрос, файлы в `out/protocols/`. Статус из документа («в работе», «согласовано», «обещано») показывается отдельной пометкой, а рабочий статус поручения по-прежнему ведёт руководитель.

Поручение попадает в календарь только после человека: в дашборде у каждой задачи есть «В задачи», у протокола — «Утвердить все». Статусы хранятся в журнале, каждое действие пишет событие; в демо календарь не трогается.

### Дожим поручений

После постановки задача живёт дальше: «В работу», «Решён» или «Не решён» с обязательной пометкой, что именно осталось. Решённые и нерешённые вопросы считаются отдельно — по протоколу и по неделе, — а протокол закрывается, когда все задачи либо решены, либо явно оставлены открытыми.

Если по ходу задача поменялась, её текст, исполнителя и срок правят прямо в строке. Правка сохраняет прежнюю формулировку в истории, требует причину и помечается «ждёт синхронизации». Кнопка «Синхронизировать» фиксирует, что руководитель в курсе: в живом режиме (`run --live`) уходит уведомление в Telegram, в демо — событие в журнале с каналом `mock`. Пока синхронизации нет, задача в дашборде подсвечена.

Составную задачу можно разложить на шаги по исполнителям — аналитик, BDM, команда CJM, смежные службы. У каждого шага свой срок, роль и зависимости: шаг без зависимостей стартует параллельно, шаг с зависимостями ждёт готовности указанных шагов и не открывается, пока они не закрыты. Для типовых сценариев («вендоры к продвижению», «витрина конкурентов», «метрики к сроку») в интерфейсе есть готовые наборы шагов с последовательностью и параллельными ветками.

## Утренний план и дайджест

`app/digest.py` собирает день руководителя: защищённые встречи и часы, решения, которые ждут именно его, дедлайны команды. Дайджест недели: сколько писем прошло без руководителя, что делегировано и кому, риски по срокам, итоги протоколов.

## Дашборд

`python -m app.cli serve` — http://127.0.0.1:8000, тёплая светлая тема, без внешних зависимостей. Значок вкладки — тёплый знак AsiStantAI: кошачья голова и литера «А» на кремовом фоне с золотым кантом; отдаётся как SVG, ICO и иконка для iOS, цвет темы — терракота.

- Входная группа: при первом открытии — «образ Аси» или «своё фото». Загруженное фото обрабатывается сразу в браузере (тон, контур, зерно в палитре Аси) и становится аватаром в шапке и на самом входе; на сцене планёрки ведущая всегда остаётся в образе Аси. Выбор хранится в localStorage браузера, кнопка «Образ» в шапке открывает выбор заново.
- Второй шаг входа у нового пользователя — «Куда Асе смотреть?»: после аватара или фото предлагаются каналы. Почта добавляется сразу (адрес, провайдер, пароль приложения; вход проверяется запросом и ящик появляется в панели «Почты»), Telegram и CRM показывают честный статус с кнопками проверки: бот и мой аккаунт — через `.env` и `tg-login`, Битрикс24 — через `BITRIX24_WEBHOOK_URL`. Шаг можно пропустить, повторно он не показывается; «Пропустить» и «Продолжить» сохраняют отметку в localStorage.
- Левая панель разделов: «Встречи», «Задачи», «Письма», «Сообщения», «CRM» — со счётчиками (протоколы, открытые задачи, черновики, непрочитанные сообщения, внешние контакты). Клик прокручивает к разделу, подсветка следует за прокруткой; на узких экранах панель становится горизонтальной строкой над содержимым.
- Карточки KPI: нагрузка из вводных — писем в неделю (50–100 в день × 5 = 250–500) и встреч в неделю (25–40), очередь черновиков, решения на руководителя, автоотправки, точность разбора, черновики со ссылками. Цифры нагрузки берутся из той же модели экономики, что и расчёт, и меняются вместе с настройками `EMAILS_PER_DAY_*` и `MEETINGS_PER_WEEK_*`.
- Шапка в тёплой графике: портрет Аси рядом с названием и карточка руководителя с портретом; при смене профиля карточка показывает новое имя, а без фото — инициалы.
- Кнопка «Ася ведёт встречу» в шапке и панели Zoom — живая планёрка голосом по данным прогона, с повесткой, таймером и передачей в Zoom (раздел «Ася ведёт встречу»).
- Очередь черновиков с фильтрами «Все / Решение / Делегировано / Авто» и поиском по теме, адресату и тексту: утвердить, поправить на месте, отклонить.
- Панели: утренний план, дайджест, экономика, журнал, протоколы, полный разбор входящих со сверкой с эталоном.
- Протоколы: поручения утверждаются по одному или все сразу — со статусом «в календаре», отдельной панелью «Календарь» и записью в журнал. Кнопка «Войти в календарь» открывает обе недели 7–18 декабря: все 50 встреч из `calendar.ics` по дням, с категорией и защищёнными блоками, и утверждённые поручения; пароли и токены не запрашиваются.
- Каждая встреча в календаре — кнопка: открывается карточка встречи с прошлым протоколом по теме (`app/calendar_links.py` сопоставляет встречу с одним из пяти архивных протоколов — по названию, иначе по категории). В карточке — решения, риски и дальнейшие шаги этого протокола, «Вопросы Аси на встрече по прошлому протоколу» и задачи с исполнителем, сроком и статусом; ссылка «Открыть карточку протокола в системе →» закрывает календарь и подсвечивает нужный протокол в панели «Протоколы». Новые поручения после встречи Ася заводит в тот же протокол. Дальше — «В работу» / «Решён» / «Не решён» с пометкой, правка текста, исполнителя и срока с историей и синхронизацией с руководителем, разложение задачи на шаги аналитика, BDM и CJM с последовательными и параллельными зависимостями.
- Блок «Задачи и поручения»: все поручения из пяти протоколов одним списком — сводка по статусам, срок, ответственный и протокол-источник. «В задачи», «В работу», «Решён» и «Не решён» работают прямо в строке и меняют тот же статус, что и карточка протокола.
- Панель «CRM · контакты»: `GET /api/crm` собирает отправителей из `inbox.csv` прогона — имя, роль, адрес, число писем, последняя тема, дата и действие Аси; внешние контакты (клиенты, вендоры, приглашения) отдельно от внутренних, адрес копируется в один клик. На датасете — 14 контактов, из них 4 внешних.
- Интеграция с CRM на примере Битрикс24 (`app/bitrix24.py`): входящий вебхук портала (`BITRIX24_WEBHOOK_URL`, право `crm`) — «Проверить Битрикс24» вызывает `profile`, «Импорт из Битрикс24» тянет контакты через `crm.contact.list`, кнопка «В Битрикс24» у внешнего контакта находит его по e-mail (`crm.duplicate.findbycomm`), создаёт при отсутствии (`crm.contact.add`) и добавляет комментарий о последнем письме в таймлайн (`crm.timeline.comment.add`). Импортированные контакты помечаются «в Битрикс24», отдельно показываются те, кого не было в прогоне. Наружу отдаются только домен портала и признак «настроен»: адрес вебхука содержит секрет и не попадает ни в статусы, ни в журнал. Без вебхука кнопки отвечают 409 и ничего не отправляют.
- Журнал выгружается в CSV по ссылке «CSV» в панели.
- Панель «Каналы»: состояние ящиков А/Б, Telegram, Zoom, Телемоста, моего Telegram и Битрикс24, кнопка «Проверить» — вход в IMAP/SMTP, `getMe` бота, авторизация MTProto, доступ к Zoom API, ссылка Телемоста и профиль Битрикс24. Кнопка «Живой прогон» снимает новые письма из IMAP. Панель «Zoom» — «Войти в Zoom» (OAuth-приложение), «Выйти» и поле постоянной ссылки; кнопка «Создать ссылку» отдаёт ссылку на встречу с копированием в один клик. Панель «Телемост» — поле постоянной комнаты и сборка ссылки с темой, временем и приглашением.
- Панель «Почты»: все ящики — из `.env` и добавленные вручную. Над списком — фильтр периода «сегодня / 3 / 7 / 30 дней / всё время»; «Непрочитанные» считает входящие за выбранный период (для «не сегодня» рядом показано, сколько из них за сегодня), «Открыть непрочитанные» показывает темы и отправителей за тот же период, «Черновики» прогоняет только непрочитанные через тот же конвейер. Ящик добавляется формой: провайдер (Gmail, Mail.ru, Яндекс, Outlook, другой), адрес, пароль приложения; пароль сохраняется локально и наружу не отдаётся. Если сервер не принял вход, причина видна прямо в строке ящика — например, Gmail просит пароль приложения из 16 символов, Mail.ru — пароль для внешних приложений; кнопка «пароль» у ящика меняет пароль и сразу проверяет вход. Добавление тоже сразу проверяет логин и сообщает результат.
- Панель «Мой Telegram»: после входа в аккаунт показывает, сколько непрочитанных и в каких диалогах за выбранный период (сегодня / 3 / 7 / 30 дней / всё время), и готовит черновики ответов по сообщениям этого периода — с копированием. Отправка только вручную из Telegram: панель ничего не отправляет.
- Панель «Личный чат»: чат руководителя, куда пишут сотрудники. Сверху — тот же фильтр периода и счётчик непрочитанных; список сотрудников с должностью, временем последнего сообщения и счётчиком новых. Клик по строке раскрывает переписку, показывает «новое / прочитано» и черновик Аси (по типу сообщения: согласование, поручение, отчёт, благодарность, к статусу). Черновик берётся в поле ответа, ответ записывается в чат и помечает входящие прочитанными; кнопки «Черновики» (пакетом по всем непрочитанным) и «Прочитать всё». Входящие сообщения хранятся в локальной SQLite; автоотправки нет — записанный ответ отправляется вручную.
- Переключатель профиля: второй руководитель подключается файлом, без изменений в коде.

Кнопки подписаны «демо» и не выдают себя за реальную отправку.

## Ася ведёт встречу

Кнопка «Ася ведёт встречу» в шапке и в панели Zoom открывает сцену планёрки: Ася говорит вживую по данным текущего прогона. Реплики собирает `app/meeting.py` из метрик, сводки и прогресса поручений — цифры совпадают с журналом и руками не пишутся. Озвучивает системный русский голос Windows через SAPI (`app/voice.py`), WAV кэшируется в `data/voice/`; лицо — портрет Аси в SVG, губы и веки двигаются по громкости звука, есть дыхание и моргание. Звук декодируется в WebAudio; если браузер не даёт его воспроизвести, включается `speechSynthesis`. Повестка из шести пунктов подсвечивает текущую тему, таймер считает минуты, пауза, продолжение и «Следующий пункт» работают как в плеере. Сервер отдаёт только реплики сценария: `POST /api/avatar/say` возвращает 403 на свободный текст, поэтому озвучить чужие слова через страницу нельзя.

**Вход в комнату.** В панелях Zoom и Телемост и на сцене встречи есть поле ссылки и кнопка «Подключиться»/«Войти»: ссылка проверяется по домену и пути комнаты, локально сохраняется в `data/rooms.json` (0600) и сразу открывается в новой вкладке (`POST /api/meeting/join`). На публичном стенде ссылка открывается, но не сохраняется, чтобы посетитель не переписал комнату; сохранённая комната локально открывается по `GET /api/join/{provider}` — на стенде этот адрес отдаёт 404, чтобы личная ссылка не утекала. Пароли Zoom и ключи приложений по-прежнему не запрашиваются.

**Протокол встречи.** По кнопке «Завершить» система сохраняет протокол: дата, длительность, руководитель, неделя, канал (Zoom/Телемост) и повестка с пометками «освещено / не рассмотрено». Запись ложится в SQLite (`meeting_minutes`), показывается модальным окном, отдаётся как Markdown (`GET /api/minutes/{id}.md`) и доступна из панели «Протоколы встреч» кнопкой «Все протоколы Аси» и по `GET /api/minutes`. В журнал пишется «встреча с Асей проведена» с номером протокола. Решения и поручения утверждает руководитель, автоотправок нет.

**Все протоколы и задачи по встрече.** Кнопка «Все протоколы Аси» открывает список всех сохранённых встреч: дата, длительность, канал, сколько пунктов освещено и сколько задач поставлено и закрыто. Любой протокол открывается из списка, а кнопка «Все протоколы» возвращает к перечню. В каждом протоколе есть раздел «Задачи по встрече»: задачу ставят к конкретному пункту повестки или ко всей встрече, с исполнителем и сроком; список показывает статус «выполнено / в работе» и переключает его одним кликом (`POST /api/minutes/{id}/tasks`, `POST /api/minutes/{id}/tasks/{task_id}/state`, таблица `meeting_tasks`). Поставленные задачи попадают в Markdown-выгрузку протокола разделом «Задачи по встрече» и пишутся в журнал. Автоотправок исполнителю нет.

**Zoom.** «Открыть Zoom» ведёт на `GET /api/zoom/open`: локально (Host `127.0.0.1` или `localhost`) — сразу в сохранённую комнату, на публичном стенде — на страницу входа Zoom, чтобы личная ссылка не утекала. Встречу Ася проводит с демонстрацией этого окна: голос идёт с машины, участники видят и слышат её вживую. Ботом-участником Zoom она не является: вход в комнату от имени аккаунта требует ключей приложения Zoom (OAuth или Server-to-Server) либо вашей постоянной ссылки — они задаются в `.env` или в панели «Zoom».

## Живые каналы: почта, Telegram, мой Telegram, Zoom, Телемост, Битрикс24

`app/live.py` — адаптеры без внешних зависимостей: `imaplib`, `smtplib`, Telegram Bot API и REST Битрикс24 через `urllib`. Всё выключено, пока в `.env` пусто; демо на датасете работает как раньше.

**Почта.** В `.env` заполняются `MAIL_A_IMAP_HOST`, `MAIL_A_SMTP_HOST`, `MAIL_A_USER`, `MAIL_A_PASSWORD` и, при необходимости, такой же блок `MAIL_B_*`. Порт 465 — SSL, иначе STARTTLS. Живой прогон забирает последние `MAIL_FETCH_LIMIT` писем из INBOX, пропускает уже виденные (таблица `seen_messages` в журнале), разбирает их тем же конвейером и отмечает UID прочитанными только после успешного прогона. Письма от собственного адреса пропускаются.

**Свои ящики.** Дополнительные ящики добавляются в панели «Почты» или через `POST /api/mailboxes`: провайдер задаёт IMAP/SMTP-хосты, можно указать их вручную. Реестр лежит в `data/mailboxes.json` (в `.gitignore`, права 0600), пароли в API, статусы и журнал не попадают — только признак `password_set`. Gmail требует пароль приложения при включённой двухэтапной проверке, Mail.ru — «пароль для внешних приложений», Яндекс — пароль приложения и включённый IMAP. Непрочитанные считаются запросом `UID SEARCH UNSEEN`; списки и тела читаются через `BODY.PEEK`, поэтому письма остаются непрочитанными, пока вы не откроете их сами. «Черновики» по непрочитанным прогоняют только их и не трогают остальную очередь. Окно непрочитанных — фильтр периода: сегодня, 3, 7, 30 дней или всё время; для почты в `UID SEARCH` добавляется `SINCE` с датой начала окна, поэтому сервер не отдаёт лишние письма.

**Отправка.** Утверждение живого черновика отправляет письмо через SMTP того ящика, откуда пришло исходное письмо: ответ клиенту — с адреса руководителя, письмо из ящика Б — с ящика Б. Черновик-решение (эскалация самому руководителю) письма не имеет: он просто утверждается и уходит уведомлением в Telegram. Если для делегирования нет адреса в `data/kuznitsa/contacts.csv` (колонки `name,email`), черновик утверждается без отправки с пометкой причины. Ошибка SMTP не помечает черновик утверждённым — его можно повторить.

**Telegram.** Бот принимает `/status`, `/drafts`, `/approve <id>`, `/reject <id>`, а в `/drafts` — inline-кнопки «Утвердить»/«Отклонить». Команды выполняются только из чатов allow-list (`TELEGRAM_ALLOWED_CHATS`, по умолчанию — `TELEGRAM_CHAT_ID`); `/start` и `/id` отвечают любому и показывают его `chat_id`, чтобы было что внести в allow-list. Уведомления: итог живого прогона и факт отправки письма. Запуск слушателя — `python -m app.cli tg-listen`, остановка — Ctrl+C.

**Мой Telegram.** `GET /api/telegram/user/unread` и `tg-unread` считают непрочитанные по диалогам за выбранный период: для «сегодня / 3 / 7 / 30 дней» непрочитанным считается входящее сообщение не старше начала окна, поэтому счётчик и основа черновика — свежие сообщения, а не вся история диалога. Для «всё время» — родные счётчики Telegram. Черновики (`POST /api/telegram/user/drafts`, `tg-drafts --period`) строятся по выбранному входящему; отправка только вручную из Telegram.

**Личный чат руководителя.** Панель «Личный чат» — таблица `manager_chat` в `data/asistant.db`: входящие от сотрудников, ответы руководителя и отметки прочитанного. У сообщения есть направление `in/out`, время и флаг прочитанного; счётчики и переписка считаются за выбранный период. Список сотрудников — из данных компании, к нему можно добавить сообщение от любого сотрудника кнопкой «Написать от сотрудника». Черновик ответа строит `app/chat.py` по типу сообщения (согласование, поручение, отчёт, благодарность, статус) — это шаблон, а не отправка. «Записать ответ» добавляет исходящее и помечает входящие прочитанными. Демо-сообщения появляются только в пустой таблице. Мост «сотрудник → Telegram-бот» выключен до настройки бота; автоотправок нет.

**Zoom.** Три режима без пароля Zoom-аккаунта. Вход через приложение: `ZOOM_CLIENT_ID`, `ZOOM_CLIENT_SECRET`, `ZOOM_REDIRECT_URI` (redirect — `http://127.0.0.1:8000/api/zoom/callback`), затем кнопка «Войти в Zoom» в дашборде или ссылка из `zoom-login-url`; токен ложится в `data/zoom_oauth.json` (0600, `.gitignore`), обновляется сам, «Выйти» его удаляет — встречи создаются от вашего имени. Server-to-Server OAuth (`ZOOM_ACCOUNT_ID` + `ZOOM_CLIENT_ID` + `ZOOM_CLIENT_SECRET`) создаёт встречи от приложения. Постоянная ссылка `https://zoom.us/j/…` вставляется в панели Zoom (хранится в `data/rooms.json`, 0600) или в `ZOOM_PERSONAL_LINK`; работает без сети. Ссылка создаётся человеком: кнопкой «Создать ссылку», командой `zoom-link` или `POST /api/zoom/meeting`; событие пишется в журнал. Автоматических приглашений нет — письмо со ссылкой уходит только как обычный черновик после утверждения. Пароль Zoom нигде не запрашивается и не хранится.

**Телемост.** У Телемоста нет публичного API создания встреч, поэтому канал работает от постоянной комнаты: откройте telemost.yandex.ru, создайте встречу и вставьте ссылку (`https://telemost.yandex.ru/j/…`) в панели «Телемост» или в `TELEMOST_LINK`. Система проверяет домен и путь комнаты, хранит ссылку в `data/rooms.json` (0600, `.gitignore`) и собирает к ней тему, время и текст приглашения. Ссылка и приглашение возвращаются кнопкой «Ссылка Телемоста», командой `telemost-link` или `POST /api/telemost/meeting`; событие пишется в журнал. Гостевая ссылка Телемоста действует 24 часа, поэтому для стабильной работы нужна комната вашего аккаунта. Наружу ничего не отправляется.

**Битрикс24.** CRM подключается входящим вебхуком портала: Битрикс24 → CRM → Настройки → Разработчикам → Другое → Входящий вебхук, право `crm`. Полученный адрес `https://<портал>.bitrix24.ru/rest/<id>/<код>/` кладётся в `BITRIX24_WEBHOOK_URL` (`.env`, в git не попадает). Клиент `app/bitrix24.py` шлёт POST на `<method>.json` и разбирает ответ REST. «Проверить Битрикс24» вызывает `profile` и показывает портал и пользователя вебхука; «Импорт из Битрикс24» читает контакты (`crm.contact.list`: имя, e-mail, телефон, компания); «В Битрикс24» у внешнего контакта ищет его по e-mail (`crm.duplicate.findbycomm`), создаёт при отсутствии (`crm.contact.add`) и пишет комментарий к последнему письму в таймлайн (`crm.timeline.comment.add`). Адрес вебхука — секрет: наружу и в журнал уходят только домен портала, признак «настроен» и идентификатор контакта. Без вебхука все три эндпоинта отвечают 409 и ничего не отправляют; ошибки сети и API — без токена в тексте. Автоотправок нет: интеграция вызывается только кнопкой человека.

**Мой Telegram (MTProto).** Бот видит только сообщения, адресованные ему, поэтому личные непрочитанные считаются через MTProto: `TELEGRAM_API_ID` и `TELEGRAM_API_HASH` из my.telegram.org, затем один раз `python -m app.cli tg-login` — телефон и код вводятся в терминале. Сессия `data/telegram_user.session` и подпись `telegram_user.json` лежат локально, в `.gitignore`, с правами 0600. История читается без пометки прочитанным: `messages.getHistory`, а не отметка о прочтении. Непрочитанные — `tg-unread` / `GET /api/telegram/user/unread`, черновики ответов — `tg-drafts` / `POST /api/telegram/user/drafts`; в журнал попадают только числа диалогов и черновиков, без текстов. Отправка — только вручную из Telegram.

Секреты читаются только из `.env` и никуда не выводятся: ни в `/api/channels`, ни в журнал, ни в текст ошибок. В архив `.env` не попадает, в поставке только `.env.example`.

## Ограничения и этика

Текстовый помощник без клонирования голоса и лица. На сцене встречи говорит системный русский голос Windows, лицо — рисованный портрет Аси: её запись и фото третьим лицам не передаются, фотореалистичное видео в поставку не входит. Своё фото из входной группы обрабатывается локально в браузере и хранится только в его localStorage — на сервер оно не уходит. Отправка — только после подтверждения человеком: автоотправок нет ни в демо, ни в живом режиме. Чувствительные темы (деньги, кадры, обязательства перед клиентами, письма руководству) автоматизации не подлежат. Персональные данные в датасете синтетические. Живые IMAP/SMTP, Telegram, мой Telegram (MTProto), Zoom, Телемост и Битрикс24 включаются только явным заполнением `.env`; без него система работает офлайн и ничего не отправляет. Адрес вебхука Битрикс24 содержит секрет: он не логируется, не отдаётся в API и в статусах виден только домен портала. Сессия моего Telegram хранится локально, в git не попадает, тексты сообщений не логируются, отправка — только вручную. Zoom-ссылка создаётся по действию человека, host-ссылка (`start_url`) не сохраняется и не показывается. Пароль Zoom не запрашивается: вход идёт на стороне Zoom, токен лежит в `data/zoom_oauth.json` (0600, `.gitignore`) и удаляется кнопкой «Выйти». Ссылки комнат Zoom и Телемоста хранятся в `data/rooms.json` (0600, `.gitignore`); из API виден только признак «сохранена», а введённая вручную ссылка возвращается только тому, кто её ввёл, и на стенде не сохраняется. Протоколы встреч лежат в локальной SQLite рядом с журналом и не содержат паролей и токенов. Личный чат руководителя хранится в той же локальной базе (`manager_chat`), наружу не отправляется, автоответов нет; мост «сотрудник → Telegram-бот» выключен до настройки бота.
